# موارد آزمون و نتیجه واقعی اجرای آن‌ها

**قاعده ثبت:** هیچ موردی که اجرا نشده باشد، «موفق» علامت نخورده است. موارد
«خودکار» با فرمان‌های زیر اجرا شده‌اند و موارد «دستی» نیازمند اجرا در مرورگر توسط
دانشجو هستند.

```bash
npm run test           # هر سه مجموعه
npm run test:domain    # آزمون لایه دامنه (بدون DOM)
npm run test:render    # آزمون دود رندر مسیرها
npm run test:ui        # آزمون یکپارچه رابط کاربری روی DOM واقعی (jsdom)
```

### نکته فنی ابزار آزمون
در jsdom رویداد خام `input` به سامانه رویداد React نمی‌رسد (برخلاف کلیک که می‌رسد).
بنابراین در `tests/support/dom-helpers.ts` مقدار ورودی با setter نمونه‌ساز نوشته
می‌شود و سپس `onChange` ثبت‌شده روی همان گره فراخوانی می‌گردد؛ مسیر منطقی
کامپوننت عیناً اجرا می‌شود و نتیجه قطعی است.

## ۵. نکته روش‌شناختی

در جریان نوشتن آزمون‌ها سه دسته شکست رخ داد و تفکیک آن‌ها آموزنده است:

۱. **کد درست، فرض آزمون غلط.** آزمون `T-11` و `T-15` شکست خوردند چون داده پایه از
   قبل یک درخواست باز برای همان خریدار روی همان آگهی داشت و قاعده «ضد درخواست
   تکراری» به درستی عمل می‌کرد. آزمون‌ها به آگهی بدون درخواست باز منتقل شدند و
   `T-11ب` مخصوص سنجش همان قاعده اضافه شد. همین اتفاق در `UI-05` هم تکرار شد:
   آزمون سراغ درخواست قدیمی‌تر رفته بود، در حالی که فهرست بر اساس تازگی مرتب است.

۲. **نقص واقعی کد که آزمون آن را پیدا کرد.** آزمون `UI-13` نشان داد حذف هم‌زمان چند
   رکورد نمونه قالب تنها یک رکورد را پاک می‌کند؛ علت، به‌روزرسانی غیرتابعی وضعیت در
   فرم اعتبارسنجی و خواندن از وضعیت کهنه در لایه مخزن بود. هر دو اصلاح شدند
   (`StoreProvider` با ارجاع به آخرین وضعیت، و `setForm` با به‌روزرسانی تابعی).

۳. **محدودیت ابزار آزمون، نه محصول.** رویداد خام `input` در jsdom به React نمی‌رسد؛
   راهکار در بخش «نکته فنی ابزار آزمون» توضیح داده شده است.
