### عنوان کسب‌وکار
بازارگاه تخصصی B2B مدیریت و فروش موجودی مازاد پارچه.

### بیانیه ارزش پیشنهادی
تارنو موجودی مازاد و راکد پارچه را از انبار کسب‌وکارها به یک عرضه ساختاریافته و
قابل مقایسه تبدیل می‌کند؛ فروشنده بدون اجبار به فروش یک‌جا نقد می‌شود و خریدار
بدون طی چرخه تماس و استعلام، مشخصات فنی و وضعیت کیفی را پیش از مذاکره می‌بیند.

### سه تمایز اصلی
1. **شناسنامه فنی استاندارد پارچه** — فیلدهای فنی الزامی و وابسته به دسته (برای پارچه مبلمان «چرخه سایش»، برای پوشاک «گراماژ و کاربرد»).
2. **فروش بخشی از موجودی با دفتر رزرو** — تفکیک موجودی به «قابل عرضه / رزروشده / فروخته‌شده» با جلوگیری از بیش‌فروشی.
3. **مدیریت چرخه عمر موجودی مازاد** — تاریخچه موجودی، درخواست‌ها، پیشنهادهای قیمت، سفارش‌ها و تراکنش‌های قابل حسابرسی.

## ۲. پشته فناوری

| لایه | انتخاب | دلیل |
| --- | --- | --- |
| کتابخانه رابط کاربری | React 18 | مدل کامپوننتی و اکوسیستم آشنا |
| زبان | TypeScript (strict) | قرارداد داده دامنه در زمان ترجمه بررسی می‌شود |
| ابزار ساخت | Vite 5 | ساخت سریع و خروجی ایستا بدون نیاز به سرور |
| استایل | Tailwind CSS 3 + توکن‌های CSS | یک نقطه کنترل تم روشن/تاریک |
| مسیریابی | React Router 6 (`HashRouter`) | اجرا روی هر میزبان ایستا بدون تنظیم rewrite |
| انیمیشن | Framer Motion 11 | حرکت‌های روایی پرونده تحلیلی |
| مدیریت وضعیت | Context + سرویس‌های خالص دامنه | قاعده کسب‌وکار از رابط کاربری جدا می‌ماند |
| ذخیره‌سازی | `LocalStorage` با درایور ماژولار | استقرار بدون سرور؛ آماده مهاجرت به Supabase |
| نمودارها | SVG دست‌نویس | کنترل کامل روی RTL، ارقام فارسی و رنگ‌های تم |
| آزمون | اجراکننده سبک خودنوشت + jsdom | سه لایه آزمون: منطق دامنه، رندر مسیرها و تعامل واقعی با DOM |

**چرا هیچ CMS یا فروشگاه‌ساز استفاده نشده است؟** صورت پروژه آن را ممنوع کرده و تمام
لایه‌های نرم‌افزار در این مخزن کدنویسی شده‌اند.

## ۳. راه‌اندازی محلی

نیازمندی: **Node.js نسخه ۲۲ یا بالاتر** (آزمون یکپارچه رابط کاربری به jsdom ۳۱ و پشتیبانی zstd در Node ۲۲ نیاز دارد؛ ساخت و اجرای خود سامانه با Node ۲۰ هم کار می‌کند).

```bash
git clone https://github.com/rouhi-dev/tarno.git
cd tarno
npm install          # نصب وابستگی‌ها
npm run dev          # اجرای سرور توسعه روی http://localhost:5173
```

ساخت و پیش‌نمایش نسخه تولیدی:

```bash
npm run build        # بررسی تایپ + ساخت در پوشه dist/
npm run preview      # پیش‌نمایش خروجی ساخت روی http://localhost:4173
```

فایل نمونه متغیرهای محیطی: `.env.example`
در فاز ۱ هیچ متغیر محیطی اجباری وجود ندارد؛ این فایل برای مهاجرت آینده به
پایگاه داده ابری از پیش آماده شده است.

### سناریوی کامل معامله (مسیر پیشنهادی ارزیاب — حدود ۳ دقیقه)

| گام | حساب | اقدام | نتیجه مورد انتظار |

| ۱ | `seller@tarno.ir` | «ثبت آگهی جدید» ← دسته «پارچه مبلمان» ← پر کردن فیلدها ← ثبت | آگهی با وضعیت «در انتظار تأیید» ساخته می‌شود |
| ۲ | `admin@tarno.ir` | «پنل داوری سامانه» ← تأیید و انتشار | وضعیت آگهی «فعال» می‌شود |
| ۳ | `buyer@tarno.ir` | «بازارگاه» ← آگهی ← مقدار معتبر ← «ثبت درخواست خرید» | درخواست با وضعیت «در انتظار بررسی فروشنده» ثبت می‌شود؛ موجودی تغییر نمی‌کند |
| ۴ | `seller@tarno.ir` | «درخواست‌های خرید» ← «پذیرش و پیشنهاد قیمت» | وضعیت درخواست «در انتظار تأیید خریدار» می‌شود |
| ۵ | `buyer@tarno.ir` | «درخواست‌های من» ← «تأیید پیشنهاد و ایجاد سفارش» | سفارش ساخته و مقدار از «قابل عرضه» به «رزروشده» منتقل می‌شود |
| ۶ | `buyer@tarno.ir` | «سفارش‌ها و پرداخت» ← «پرداخت موفق» | رزرو به «فروخته‌شده» منتقل و تراکنش `commit` ثبت می‌شود |
| ۶ب | `buyer@tarno.ir` | همان گام با «پرداخت ناموفق» | رزرو آزاد و به «قابل عرضه» بازمی‌گردد (تراکنش `release`) |

### آزمون قواعد و خطاهای مرزی
- **حداقل سفارش:** مقدار کمتر از حداقل سفارش → رد با پیام روی همان فیلد.
- **سقف موجودی:** مقدار بیشتر از موجودی قابل عرضه → رد با اعلام موجودی واقعی.
- **تضاد منافع:** ورود با حساب فروشنده و تلاش برای خرید آگهی خودش → مسدود.
- **درخواست تکراری:** ثبت دو درخواست باز روی یک آگهی → رد با ارجاع به کد درخواست باز.
- **شفافیت کیفی:** انتخاب درجه B یا C بدون توصیف ایراد → ثبت آگهی مسدود.
- **دامنه مقادیر فنی:** عرض ۹۰۰ سانتی‌متر یا گراماژ ۵۰۰۰ → رد با اعلام بازه مجاز.
- **رد بدون دلیل:** رد درخواست یا رد آگهی با دلیل خالی → مسدود.
- **حالت خالی:** اعمال ترکیب فیلتری بی‌نتیجه در بازارگاه → نمایش حالت خالی با پیشنهاد اصلاح.

### آزمون‌های خودکار

```bash
npm run test           # هر سه مجموعه
npm run test:domain    # ۳۷ آزمون روی لایه دامنه (بدون DOM)
npm run test:render    # ۲۴ رندر مسیر برای کشف خطاهای اجرایی رابط کاربری
npm run test:ui        # ۱۸ آزمون یکپارچه: کلیک و تایپ واقعی روی DOM (jsdom)
```

نتیجه آخرین اجرا: **۳۷ موفق از ۳۷**، **۲۴ رندر سالم از ۲۴** و **۱۸ موفق از ۱۸** —
در مجموع ۷۹ آزمون خودکار، همه موفق.

آزمون یکپارچه رابط کاربری، چرخه کامل معامله را با کلیک و تایپ واقعی اجرا می‌کند:
ورود، ثبت آگهی با اعتبارسنجی، داوری مدیر، درخواست خرید، پیشنهاد قیمت، رزرو و
پرداخت موفق و ناموفق. دو مورد باقی‌مانده (چیدمان موبایل و ترتیب فوکوس صفحه‌کلید)
به موتور چیدمان مرورگر نیاز دارند و با برچسب «اجرا نشده» در `docs/TEST_RESULTS.md`
ثبت شده‌اند.

## ۶. ذخیره‌سازی داده — چگونه کار می‌کند؟

- کل وضعیت سامانه در یک شیء JSON با کلید `tarno.db.v1` در `LocalStorage` مرورگر نگه داشته می‌شود.
- در نخستین بازدید، داده پایه (Seed) ساخته و ذخیره می‌شود: ۱۰ آگهی، ۶ دسته پارچه، ۵ حساب کاربری، ۴ پرونده کسب‌وکار و ۲ درخواست خرید باز.
- هر تغییر وضعیت از سرویس‌های دامنه عبور می‌کند و سپس پایدار می‌شود؛ با بازخوانی صفحه (F5) داده از بین نمی‌رود.
- تمام دسترسی‌ها به حافظه در `try/catch` هستند: اگر مرورگر در حالت ناشناس باشد یا حافظه مسدود شده باشد، برنامه با حافظه موقت ادامه می‌دهد و وضعیت آن را در «ابزار داده و سلامت» اعلام می‌کند.
- نسخه اسکیما ذخیره می‌شود؛ در صورت ناسازگاری نسخه یا خرابی داده، به جای خطای اجرایی، داده پایه بازسازی می‌شود.
- دکمه **«بازنشانی داده پایه»** در «ابزار داده و سلامت» سامانه، همه چیز را به وضعیت اولیه برمی‌گرداند تا سناریوها تکرارپذیر بمانند.
- تنها نقطه تماس با حافظه مرورگر، فایل `src/lib/store/repository.ts` است؛ بنابراین مهاجرت به Supabase در فازهای بعد فقط همین فایل را تغییر می‌دهد.

## ۸. استقرار

خروجی ساخت یک بسته کاملاً ایستا در پوشه `dist/` است و به سرور یا پایگاه داده نیاز ندارد.
مسیریابی از نوع `HashRouter` است، بنابراین هیچ تنظیم بازنویسی مسیر لازم نیست.

### Vercel
```bash
npm i -g vercel
vercel            # Build Command: npm run build — Output Directory: dist
vercel --prod
```

### Netlify
```bash
npm i -g netlify-cli
netlify deploy --build --prod    # publish directory: dist
```

### GitHub Pages (استقرار فعال این پروژه)
گردش‌کار `.github/workflows/deploy-pages.yml` با هر push روی شاخه `main` به صورت
خودکار آزمون‌ها را اجرا، پروژه را می‌سازد و روی GitHub Pages مستقر می‌کند.

گام‌های تفصیلی و نکات هر بستر در `docs/DEPLOYMENT.md` آمده است.

> **قانون فریز ۴ ساعته:** آخرین کامیت و استقرار باید حداکثر ۴ ساعت پیش از نوبت
> تحویل ثبت شده باشد.
